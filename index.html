Spec of Record (SoR)

  • Sebastian RathSourceCC BY 4.0MIT

Spec of Record is a development philosophy and toolchain for AI-built software, aimed at mid-sized to large projects. It turns the spec into a centralized design document that always stays in sync with the code, so team members with different areas of expertise can understand, review and change the software together. You write what your software should do in plain language, an AI agent turns it into code, and each piece of code stays linked to the statements of the spec and to its test results.

Why use SoR?

The reason a code line exists usually lives in a verbose commit message, a Jira ticket or a Slack message, not in the code itself. AI can write code quickly and loves to rewrite larger parts of the source code because it feels like it. AI agents mostly find context with a keyword search like grep, so when someone makes a change, they either miss things they should address or change too much.

Over time, the team loses track of how their software actually works. In a review, you face hundreds of new lines that nobody can meaningfully trace, and you send them back to the AI with "fix this" or wave them through with an LGTM. The AI needs help too. Round after round of fixes, it keeps changing things until the code has moved away from its original purpose and nobody knows what it is changing anymore. It is a quality and liability risk.

Here is what Spec of Record changes, for people and AI:

  • The sor/ folder is the new src/, hierarchically structured like source folders used to be, only more compact. It holds up-to-date spec files, each covering one responsibility. There is no stack of old versions, so everyone knows what the software does now and how.
  • Engineering, QA and UX each work in their own field of expertise while sharing a common design document. You decide what the software does and stay its author.
  • A change to one clause in a spec file changes only the necessary code and reduces drift. It gives AI tremendous guard rails for attention and context.
  • Several agents can work in parallel, because each claims its spec clauses before touching anything, and a clause someone else holds is refused.
  • Every line of code names its origin in the spec and every finished build keeps its test results. "Why is this here?" and "Was it tested?" become easy lookups.

Where it fits in spec-driven development

Spec-driven development means writing down what the software should do and letting an AI write the code. The term is overloaded, so it helps to be clear about its meaning. The difference is what happens to the spec after the code exists. Birgitta Böckeler of Unblocked describes three levels:1

LevelWhat happens to the spec
Spec-firstWritten to get one task done, then left behind.
Spec-anchoredKept after the task and updated as the feature changes.
Spec-as-sourceThe only thing people edit. Nobody touches the code.
Spec-of-recordThis proposal.

Where spec-driven development goes wrong

A design document is only useful when it's up to date. Spec drift is what happens when the spec says one thing, the code does another, and nobody can tell which is right. It creeps in one small change at a time.

Most spec-driven development is spec-first, which makes it a good place to look at the potential traps. The spec is written for one task and then put away. The code keeps changing, and the spec stays as it was.

Take a game. Its spec says the player needs 3 keys to open the exit, and the designer asks for 5. The AI changes the code, and nobody updates the spec, because nobody asked or the AI forgot. Now the spec says 3, the game asks for 5, and no one knows what should be true.

Spec-first has a second trap, and it catches the teams that avoid the first one. To keep the spec up to date, they write a follow-up spec for every change, so you end up with SPEC.md, then SPEC-2026-01-08.md, then another one. To learn what the software does today, you read them all in the right order. They become incredibly verbose and eventually no one reads them anymore.

In spec-as-source, people edit only the spec and the code is generated from it. You can't fix the code by hand, so every fix goes through the spec, and because an AI does not generate the same code twice,1 the result can come back different each time.

Spec of Record extends spec-as-source and allows hand edits on purpose. You can change either side, the spec or the code, and the other one is updated to match. Finished code is kept, so a change to a clause rewrites only that clause's code, and the clause's tests check the result. The bundled command line interface (CLI) of SoR enforces this. It checks that spec and code agree, blocks AI edits that skip the clause, and flags any mismatch until it is fixed.

How it works

The specs are written in plain language. You edit the spec and the AI edits the code to match. If you edit the code, the AI edits the spec to match.

The spec is split into parts, one Markdown file for each area of the software, such as a game's logic or its multiplayer networking. Each part says why it exists and lists its rules, its approach, what it needs from and gives to other parts, and its tests.

The unit is a clause, which is one rule, one number or one table row. Every clause comes with a marker, a short comment above its code that names the clause. Below is a clause and the code built from it, so you can see each side point at the other.

With that association in place, a change is guaranteed to stay local. Say you want the player to move only on every second key press. You change that one sentence, and the AI updates just the code blocks marked with that clause.

If you know how a compiler works, you can apply that concept to Spec of Record, with the AI playing the compiler.

Several agents can work on one project at once. Each sub-agent can claim a spec clause together with its code blocks, change the clause first and then the code, lock the result and release the claim. A claim on a clause that someone else holds is refused.

A real compiler gives the same output every time, so it can throw that output away and start over. An AI cannot, so Spec of Record keeps finished code.

Tools can follow the marker links too. An editor extension jumps from a spec to its code and back, and the sor CLI gives an AI or a script the same answer as text or JSON. A clause can also reach further back, to a source outside the code such as a Figma design.

In your editor

The VS Code extension shows these links on a sample project. You do not need it to use Spec of Record, but it is a handy way to see them.

  • Open a spec and each clause shows the code regions built from it, with links to them.
  • Open the code and each region shows its clause and whether the two still agree.

What you get

Beyond the editor extension, Spec of Record comes with a CLI, sor, and an edit guard for your AI agent. Here is what they do:

  • The change list shows what changed since the last build and which code needs rebuilding.
  • The edit guard stops the AI from changing code before its clause.
  • The test runner runs each clause's tests and tells you how many clauses pass.
  • The build record remembers, for every clause, whether its tests passed, so you can look up later what was tested.
  • For AI, scripts and CI, the CLI answers directly. For example, sor markers says which clause a line came from, or which code a clause produced. Other commands show a clause with its code and map the spec.

The build record

If you manage a team or answer to auditors, this is the section for you.

The build record is a checkpoint. Each time a piece of work is finished and the specs, the code and the tests agree, the tool saves one, together with the test results. Later it compares the project with that checkpoint to see what changed, and you can look up what was tested. It is a plain file in your repository, so version control keeps every earlier checkpoint.

QuestionAnswer
Why does this line of code exist?Its marker names the clause it serves.
What code does this clause make?The clause points to all of it.
What did this change affect?The change list shows it.
Who changed it, and when?Version control shows it. Code changed without its clause is flagged, with author and date if you use git.
Was it tested?The build record stores the results, and version control keeps the history.
Does every result come from an automated test?Yes, except for checks a person signed off by hand. An AI cannot sign off.

That helps with reviews, handovers and compliance checks, anywhere a change has to be explained later.

Common questions

Is this more documentation to maintain?

No, it replaces the documents you would otherwise write. The spec is what you edit. A change edits a clause, and a new feature adds clauses, or a new part, to the same set of files. There is no second copy buried in Confluence or Slack.

Do I have to convert my existing project?

No. Start with the one thing you are about to change, as in the install steps at the top. The rest of the code stays as it is.

Where do the specs live?

In a sor/ folder next to your code, as plain Markdown files you commit with it. There is no service to run and no account to create.

Will building my entire project with SoR create a dependency?

No, there is zero dependency. The code is plain source with marker comments in it, so you can delete the specs and carry on from the source, or switch to another engineering approach.

Which languages and tools work?

It is agnostic to language, framework and editor. Today the workflow ships as a Claude Code plugin, and other agents and editors are open for contributions.

What if I change the code myself?

Go ahead. Your change stays. The tool flags it as code changed without its clause (with author and date if you use git), and the AI rewrites the clause to match what you did.

What if the AI builds something wrong?

The clause's tests fail, and the code is fixed until they pass. Clauses with no passing test are listed, so a gap is visible instead of hidden.

Can several people or agents work at once?

Yes. Agents in the same project claim the clauses they are working on, and a second claim on the same clause is refused. People on different machines coordinate through version control, the way they do now.

# Exit

Why The way out: find enough keys and the door opens.

## Rules

layout 4 keys lie around the room, and the exit sits in the top right corner.

door The player must collect at least 3 keys to open the exit, and is told how many are still missing.

pickup Touching a key picks it up, and a key can only be picked up once.

win Walking into the open exit wins the run.

## Approach

How it looks. The exit is grey until it opens, then green. The corner shows how many keys are still missing.

Out of scope. Coloured keys and locked doors elsewhere.

## Contract

Needs player/movement/position where the player is, from the player part.

## Tests

door With 2 keys the exit stays shut and 1 key is missing. With 3 it opens.

do: pick up 2 keys

expect: the exit is shut, 1 key is missing

do: pick up a 3rd key

expect: the exit is open

pickup Touching the same key twice counts once.

do: touch the same key twice

expect: the player holds 1 key

# Maze game

Why A small maze game: collect keys, keep away from the monsters, reach the exit.

## Rules

goal A run is won by reaching the open exit.

loss A run is lost when the player has no lives left.

## Approach

Parts. The player walks and has lives, the monsters chase, the level has the exit, and the run ties them together turn by turn. Each is its own file.

Out of scope. More than one level, saving a run.

## Tests

goal Reaching the open exit with 3 keys wins the run.

do: walk into the open exit with 3 keys

expect: the run is won

# Movement

Why The player walks around the room one step at a time.

## Rules

step One key press moves the player 20 px.

walls The player cannot leave the room, which is 500 px wide and tall.

## Contract

Gives position where the player is, and near: two things are near when they are closer than 24 px.

## Tests

step One key press to the right moves the player 20 px.

do: press right once

expect: the player is 20 px further right

walls Walking left at the wall does not move the player.

do: press left at the wall

expect: the player has not moved

# Lives

Why The player can survive a few monster touches.

## Rules

start A new player has 3 lives.

lose A monster that touches the player costs 1 life.

out At 0 lives the run is lost.

## Contract

Gives hasLives true while the player has a life left.

## Tests

start A new player has 3 lives.

do: start a new run

expect: the player has 3 lives

lose One touch leaves 2 lives.

do: let a monster touch the player

expect: the player has 2 lives

out With 0 lives the player is out.

do: set the lives to 0

expect: the player is out

# Monsters

Why Monsters make the room dangerous.

## Rules

chase Every turn a monster steps 20 px toward the player.

touch A monster that touches the player takes a life from the player.

## Contract

Needs player/movement/position where the player is, and player/lives/lose to take a life.

## Tests

chase A monster 40 px left of the player ends 20 px closer.

do: take one turn with a monster 40 px left of the player

expect: the monster is 20 px closer

touch A monster on the player takes one life.

do: take one turn with a monster on the player

expect: the player has 1 life less

# Run

Why One turn of the game, from key press to win or loss.

## Rules

turn Each key press moves the player, picks up keys and moves the monsters.

end The run ends as soon as it is won or lost, and later key presses do nothing.

## Contract

Needs player/movement/step to walk, level/exit/pickup to take keys, monsters/monsters/chase and touch to move the monsters, and goal and loss to check the run.

## Tests

turn A key press moves everything once, and a monster that arrives takes a life.

do: press right with a monster 40 px to the right

expect: the player is 20 px further right

expect: the monster has reached the player

expect: the player has 2 lives

end A run that is over ignores key presses.

do: press right after the run is lost

expect: the player has not moved
